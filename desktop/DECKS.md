# Deck profiles and editor shortcuts

Each physical Stream32 device can keep up to 16 named profiles. The device
nickname identifies the hardware; profile names identify independent sets of
pages and keys. Selecting a profile sends all of its pages and its selected
device page to connected firmware. Offline edits remain saved and sync on the
next connection.

Existing `decks.json` files are migrated automatically. A legacy profile is
wrapped as a profile named **Default**, while its previous `name` becomes the
device nickname. Profile IDs are generated by Stream32 and do not change when
the friendly profile name is renamed.

Keys can use the built-in **Switch profile** action to select one of those
stable IDs without opening the editor. The desktop app must be running because
the host validates the profile operation, updates the selected page, and syncs
the chosen profile to the physical deck. Switch profile is also available as a
Multi Action step; switching away from the originating profile cancels all
later steps. If a target profile is deleted, the key keeps a visible
**Missing profile** reference so imports and copied keys are not silently
rewritten.

Deck export is a single-profile schema-5 file; schema-1 through schema-5 files
can be imported. Import adds and selects a named profile instead of
replacing the device's other profiles. Full backups include the complete
named-profile registry.

## Focused-app switching

Each device has exactly one default profile, and each profile has exactly one
default page. Focus switching is sticky: Stream32 selects a profile or page
only when that item has an explicit match for the focused application. An
unmatched application leaves the current profile and page unchanged. Profiles
and pages can each hold one bounded app identity per platform:

- Windows matches an executable basename or path suffix.
- macOS matches a bundle identifier, with process name as a fallback.
- Linux X11 matches `WM_CLASS`, with process name as a fallback.

Choose **Use focused app** after focusing another application to capture its
stable identity, or enter the identity manually. Manual macOS process names
use `process:App Name`; Linux values use `class:name` or `process:name`.
Matches are exact, case-normalized identities rather than scripts or regular
expressions. If more than one profile has the same match, the
lexicographically first stable profile ID wins. If more than one page in the
chosen profile matches, the lowest page index wins.

Choosing a page manually updates that profile's active page without changing
its default page. Existing schema-4 profiles migrate with their previous active
page as the default. Defaults provide deterministic initial and deletion
fallbacks; they do not trigger a focus switch for unmatched applications.

Stream32 checks focus conservatively in the background and does not switch
while its own editor is focused. Wayland has no generic focused-window API, so
automatic switching is disabled there without affecting manual profile
selection. macOS permission errors and a missing X11 `xdotool` are shown in
the profile editor.

## Key editing

The selected-key editor uses separate Appearance and Behavior sections. They
sit side by side when space permits and stack at narrow widths. Add and Rename
profile use the in-app name dialog, including inline empty and duplicate-name
errors, so the controls work in packaged sandboxed builds.

- Focus a configured deck key and press `Ctrl/Cmd+C`, `Ctrl/Cmd+X`, or
  `Ctrl/Cmd+V` to copy, cut, or paste. Text fields keep their normal shortcuts.
- Paste rewrites the key index for its destination and asks before replacing an
  occupied key.
- Drag a configured key onto another key to move it. Occupied destinations
  swap the two keys.
- While dragging, move over a page or profile tab to expose a destination on
  another page or profile.
- Copy, Cut, and Paste buttons provide the same operations without keyboard
  shortcuts.

Page actions are accepted only when their target exists in the destination
profile. Invalid cross-profile pastes and swaps are rejected without changing
either profile.

## Live key state

Live state is a RAM-only overlay on the saved key appearance. Compatible
firmware advertises `key-update`; older firmware continues to receive the base
deck and the editor reports that live state is unavailable. Live titles,
colors, state, and artwork never rewrite profile JSON or flash artwork.

- **Local toggle** flips only after its action or complete Multi Action
  succeeds. Its status is local to Stream32, not remote application truth.
- **Clock** updates the key title at minute boundaries in 12- or 24-hour format.
- **Focused app** shows a bounded application identity from the existing
  first-party focus watcher; it never exposes window titles.
- **Status command** runs a command you write and shows the appearance you gave
  its exit code, so a key can follow something Stream32 has no other way to
  know. It is the one provider that can tell you about state changed by
  something other than the deck.

Toggle on-artwork uses the same bounded image upload pipeline as base artwork,
but firmware keeps the rendered RGB565 bytes only in RAM/PSRAM. Reconnects and
base profile syncs reapply current overlays without changing the saved base.

### Status commands

Give the key up to eight exit codes, each with its own label, colors and
artwork. A script that both performs and reports an action is the usual shape:
the key's Launch action runs `audio-output.sh`, and its status command runs
`audio-output.sh --status`, which exits `0`, `1` or `2` for the output now in
use. Because the board is asked what to look like rather than told what
happened, the key stays right when the change came from somewhere else, which
a key that only flips on its own press cannot do.

The command runs on its interval and again as soon as the key's own action
succeeds, so your own press never waits out the interval it just invalidated.
Only the exit code is read: output is discarded rather than buffered, and it
never reaches a log.

These are the bounds it runs inside, because a polled command is not a pressed
one:

- Only while that deck is connected and not driven by Companion. A closed app
  or an unplugged board runs nothing.
- Never two at once for one key. A command slower than its interval stretches
  its own schedule instead of stacking shells behind itself, and the next run
  is due an interval after the answer rather than after the request.
- Killed after five seconds, along with anything it started. Killing the shell
  alone would leave the command that is actually hanging behind it, so the
  whole process group goes on POSIX and `taskkill /t` walks the tree on
  Windows. A hung command reports nothing rather than stalling the key.
- An unmatched exit code, a command that cannot run, and one that hangs are the
  same answer: the key shows the appearance you saved for it.

The command is yours and runs with your privileges, exactly like the Launch
action. The difference worth thinking about is that this one runs on a timer
rather than when you press something, so point it at something cheap that
answers quickly.

On Windows the command runs through `cmd`, and no console window appears for
it. Exit codes there are not limited to the 0-255 a POSIX wait status carries,
so `9009` for a command that does not exist and `3010` for an installer asking
for a reboot are both states you can give an appearance to. A batch file
reports through `exit /b`, and PowerShell through `exit`, which means
`powershell -NoProfile -Command "...; exit 2"` is the usual one-liner shape.

On macOS and Linux the command runs through `/bin/sh`, not the shell you use in
a terminal, and it inherits the environment Stream32 was started with rather
than the one your shell builds. On Debian and Ubuntu `/bin/sh` is `dash`, so a
one-liner written in bash syntax needs `bash -c '...'` around it; a script file
is unaffected, because its own shebang decides. On macOS that is the biggest practical
difference between the two: an app opened from Finder or the Dock is started by
`launchd` with a short PATH that leaves out `/opt/homebrew/bin` and
`/usr/local/bin`, so a Homebrew tool that works when you type it will exit
`127` here. Write the full path to it, which is worth doing anyway for
something that runs unattended. A command that drives another app through
`osascript` also needs Automation permission, which macOS asks for once, so run
it by hand before pointing a key at it.

## Multi Actions

A Multi Action runs up to 16 ordered action or delay steps. Action steps use
the same media, hotkey, Type Text, Mouse, website, launch, page, profile, and
plugin controls as regular keys. Delays are capped at 30 seconds each and two
minutes total. Multi Actions cannot be nested.

Page steps switch locally through the active device session. A sequence stops
at its first failed step, when its device disconnects, or when another named
profile becomes active. Repeated presses of the same Multi Action key do not
overlap, while other keys remain available.

## Keyboard and mouse input

**Type Text** sends up to 512 Unicode characters to the focused application.
Newlines and tabs are supported; unsafe control characters are rejected.
**Mouse** supports single/double left, right, and middle clicks, bounded
absolute or relative movement, and bounded vertical/horizontal scrolling.

Windows uses a persistent, structured `SendInput` helper. macOS uses fixed
System Events/CoreGraphics programs and requires Stream32 in **System Settings
> Privacy & Security > Accessibility**. Linux input is X11-only and requires
`xdotool`; generic Wayland input is intentionally reported as unavailable.
The action picker queries these host capabilities and displays the reason when
an action cannot run.
